이상형 · tec-session harness engineering (64p)

모델이 아니라
일하는 환경을 설계한다

AGENT = MODEL + HARNESS. 원시 LLM은 "운영체제 없는 CPU". 모델은 요리사, 하네스는 주방. 좋은 답변은 모델만이 아니라 모델이 일하는 환경에서 나온다. 이 덱은 하네스의 이상형을 제시한다 — Context · Tool · Permission · Verification 네 축.

CONTEXT

무엇을 보는가

TOOL

무엇을 쓰는가

PERMISSION

무엇을 할 수 있는가

VERIFICATION

어떻게 검증하는가

"모델이 똑똑해질수록, 일하는 환경을 설계하는 힘이 더 중요해진다." — 마무리 슬라이드

01계층 사다리 — 단순 추론기 → 자율 시스템

L1Raw LLM입력→출력, 단일 추론, 메모리·도구 없음
L2SubagentLLM core + Tool(s) + Context, 반복 루프
L3Agent Team협력 에이전트 + Orchestrator(계획·위임·집계)
L4Harness전체 제어층 = Eval/Test + Retry/Guard + Routing + 흐름제어

"계층이 올라갈수록 '모델이 혼자 할 수 없는 일'을 감싸는 인프라가 추가된다."

02왜 단순 에이전트는 실패하는가

Context Degradation

임계점 이후 크기와 추론 성능이 반비례. compact은 정보 유실. → 세션을 끊어야 한다.

Self-Evaluation Bias

자기 결과물 과대평가 → 환각. → 외부 Evaluator + 상태 외부화 필요.

컨텍스트 열화 — 1M 윈도우라도 체감 품질은 다르다

03하네스의 구성

제품급 12요소

#구성요소비유역할
1목표·성공기준주문서무엇을 끝으로 볼지
2오케스트레이션흐름표호출·실행·반영 반복
3도구 레이어손과 발검색·파일·API
4메모리업무 노트세션 안팎 정보 보관
5컨텍스트 관리책상 정리지금 볼 자료만 선별
6프롬프트 구성안건지지시·도구·메모리 조립
7출력 파싱접수 담당답변/도구호출 구분
8상태·체크포인트저장 버튼재개·되돌리기·디버깅
9오류 처리고객센터재시도·복구·개입
10가드레일·권한출입카드위험 차단·승인
11검증 루프검사관테스트·리뷰·평가
12관측성·분업CCTV로그·비용·subagent

메모리 4유형

Working Context · Semantic Knowledge · Episodic Experience · Personalized Memory

중재장치 6종

Sandboxing · Observability · Compression · Evaluation · Approval Loops · Sub-Agent Orchestration

하네스 루프 7단계

프롬프트 조립 → 추론 → 출력 분류 → 도구 실행 → 결과 패키징 → 컨텍스트 업데이트 → 반복/종료. 종료 5종: 최종답변·턴제한·토큰예산·가드레일·사람 승인.

역할 5 · 분업 3

Planner·Researcher·Builder·Evaluator·Reporter / Fork(독립조사) · Teammate(긴·병렬) · Worktree(위험한 변경)

"오류는 숨기지 말고 관찰 메시지로 돌려보낸다. 루프 품질은 모델 호출보다 각 단계 사이의 연결·검증에서 결정된다."

04패턴 카탈로그

패턴어떻게언제
GAN loop
2-agent		Generator(HTML/CSS/JS, Claude Agent SDK) ↔ Evaluator(Playwright MCP 렌더·채점), 5~15회 / ~4h자동 시각 검증 가능한 UI
3-agent loopPlanner(1~4문장→스펙) → Generator(React/FastAPI/SQLite, 한 기능씩 Git) → Evaluator(Playwright: UI→API→DB)난이도 높은 풀스택
Ralph loop컨텍스트 매 루프 초기화 + 상태 외부화: feature_list.json·progress.md·git·test report + Handoff, init.sh+smoke test검증 가능한 긴 작업. 토큰 비용 큼
Permission허용(읽기·검색) / 승인(메일·결제·삭제) / 금지(비밀번호·권한변경·개인정보). settings.json 통제 + 전 행동 로깅되돌릴 수 없는 작업 포함 시
Tool design
P1~P6		고임팩트 통합(1:1 X)·접두사 네임스페이싱·의미식별자·페이지네이션·설명 엔지니어링·실행가능 오류. 출력=상위5개 요약항상
Ralph loop 실패 방지: "너무 일찍 완료"→feature list 먼저 읽게 · "버그 둔 채 인계"→실패 로그를 progress에 · "실제 흐름 미확인"→브라우저 검증 · "매번 실행법 재탐색"→init.sh+smoke test. (Git commit = "작업 일지")

05얇은 vs 두꺼운 하네스

두께는 취향이 아니라 위험도·반복성·실패 비용에 대한 설계 결정이다.

얇음 ─────────────────────────────────────────── 두꺼움
Claude Agent SDK → OpenAI Agents SDK → CrewAI Flow → LangGraph
모델 자율성 신뢰                        흐름을 코드로 명시
단순·유연, 새 모델 이점 빨리            예측·감사 가능, 복잡 업무 통제
탐색·창작·코드보조                      규제·결제/배포·고위험·다단계

설계 전 7질문

단일 vs 멀티 · ReAct vs 계획후실행 · 강한압축 vs 풍부한컨텍스트 · 계산적 vs 추론적 검증 · 허용적 vs 제한적 · 전체 vs 최소 도구 · 얇은 vs 두꺼운

건강성 체크

① 더 강한 모델로 복잡도 없이 성능↑? ② 일부 제거해도 품질 유지? ③ 실패 시 trace/log/eval로 원인이 보임? ④ 비계 제거 후 회귀 평가 있음?

"하네스는 비계처럼 세우고, 쓰고, 걷어내고, 다시 조정한다. 성숙한 하네스는 기능을 많이 붙이는 게 아니라, 반복 가능한 운영 구조를 갖추는 것."

06보안 — 프롬프트 인젝션

유형

Direct(입력창 악성 명령) · Indirect(문서·웹 숨은 명령) · Jailbreak(역할극 우회)

3계층 방어

①입력 검증(패턴·길이·인코딩 정규화) ②권한 분리(샌드박스·최소권한·데이터/명령 분리) ③출력 검증(민감정보 필터·인간 검토·이상탐지)

핵심 원칙

"외부 데이터는 항상 '데이터'로만 취급, 절대 '명령'으로 실행 금지."

07실전 — 패턴·로드맵·계층

12 실전 패턴

단일·계획실행·생성검토·라우터·전문가팀·감독자·병렬·순차·사람승인·메모리루프·도구게이트·진화루프. 선택 기준=위험도·반복성·복잡도.
