## Part 1 · 프레임워크 덱 (이상형) — 요약

> **AGENT = MODEL + HARNESS.** 원시 LLM은 "운영체제 없는 CPU". 좋은 답변은 모델만이
> 아니라 모델이 일하는 환경에서 나온다. 4축: **Context · Tool · Permission · Verification**.

- **계층 사다리**: Raw LLM → Subagent → Agent Team → Harness(Eval/Test+Retry/Guard+Routing).
- **왜 단순 에이전트는 실패하나**: Context Degradation(임계점 후 크기↔성능 반비례) +
  Self-Evaluation Bias(자기 과대평가) → **외부 Evaluator + 상태 외부화** 필요.
  - 수치: 1M 윈도우 벤치 정확도 Sonnet 4.6 **18.5%** vs Opus 4.6/4.8 **76%**, 체감 고품질 ~100K vs ~400K.
  - Solo Agent **20분/$9**(미동작) vs Full Harness **6시간/$200**(동작). "난이도↑ → 하네스 가치↑".
- **패턴**: GAN loop(Generator↔Evaluator) · 3-agent(Planner→Generator→Evaluator) ·
  Ralph loop(상태 외부화 + Handoff) · Permission harness(허용/승인/금지) · Tool design P1~P6.
- **두께**: 얇음(Claude Agent SDK) → 두꺼움(LangGraph). "두께는 취향이 아니라 위험도·반복성·실패비용의 함수."
- 명제: **"모델이 똑똑해질수록, 일하는 환경을 설계하는 힘이 더 중요해진다."**

→ 전체: `1_이상형_프레임워크덱.md`

## Part 2 · harness-test (동료 하네스) — 요약

> **정책(policy.json v3) + 훅 강제 + 자율 JS 워크플로우 + 커맨드의 4층.** "한 작업=한
> 브랜치". 에이전트가 실수하지 못하게 가드레일을 먼저 깔고 자율 팬아웃. 덱 기준 **두꺼운** 하네스.

- **Context** ★★★ — CODEMAPS(진실원본)·worklog·ADR·active-work(진행원장). 덱의 Ralph/Handoff 구현.
- **Tool** ★★ — MCP 4종 + 스킬 7종.
- **Permission** ★★★ — policy 격자형 읽기/쓰기 경계 + guard-paths 사전검사 + 시크릿 차단.
  (단 **사람 승인 루프는 없음**)
- **Verification** ★★★ — 3중 결정론 게이트(유닛 pytest·계약 schemathesis·화면 Playwright),
  **LLM 평가자 배제, exit code만 신뢰.**
- **Orchestration** ★★★ — 15에이전트·8워크플로우·루프가드(MAX_ROUNDS+무진전감지+예산+회귀금지).
- **빈틈**: 크로스모델 없음 · 승인 게이트 없음 · MCP 전역접근 · 비용 사후 집계.

→ 전체: `2_동료하네스_harness-test.md`

## Part 3 · AutoAgent (우리 하네스) — 요약

> **Claude·Codex를 서브프로세스로 구동해 별도 타깃을 두 모델이 교대로 구현·리뷰.**
> 결정적 Python으로 감싸고, 위험 변경은 사람 승인 게이트를 통과해야 코드가 바뀐다. 덱 기준 **중간** 두께.

- **Context** ★★ — run 산출물 + checkpoint(핸드오프는 resume 한정).
- **Tool** ★ — MCP 거의 없음, 프롬프트 중립채널 중심.
- **Permission** ★★ — **사람 승인 게이트(high-risk/db)** + 권한모드 + 샌드박스 + git 베이스라인.
- **Verification** ★ — 테스트 없음 → dry-run 바이트 패리티 + **크로스모델 상호 리뷰**.
- **Orchestration** ★★ — 9역할 고정 파이프라인 + 예산 + stop-after (decompose 제한적 병렬 실행기, worktree, 라이브 미검증).
- **차별점**: 크로스모델(리뷰어=반대) · 승인게이트+resume · 외부 비침투(자동 커밋 없음) · high-risk opus/xhigh 승격.

→ 전체: `3_우리하네스_AutoAgent.md`

## Part 4 · 3자 비교 (프레임워크 렌즈)

> ⚠️ harness-test 조사 시 서브에이전트가 AutoAgent 기능을 일부 부풀렸다(자동 순서도 생성·
> 실시간 토큰 모니터링·에이전트별 MCP 능력정의는 **AutoAgent에 없음**). 아래는 실제 코드 기준 교정본.

### 4.1 4축 성숙도

| 축 | 프레임워크 이상형 | harness-test | AutoAgent |
|----|------------------|--------------|-----------|
| **Context** | 목표문서+지도+메모리+핸드오프 | ★★★ CODEMAPS·worklog·ADR | ★★ run 산출물·checkpoint |
| **Tool** | 최소·고임팩트·설명 엔지니어링 | ★★ MCP 4 + 스킬 7 | ★ MCP 거의 없음 |
| **Permission** | 허용/승인/금지 + 경계 설계 | ★★★ 정책 경로가드+시크릿차단 (승인루프 약함) | ★★ **사람 승인 게이트**+권한모드+샌드박스 |
| **Verification** | 계산적 테스트 + 외부 Evaluator | ★★★ 3중 결정론 게이트 | ★ dry-run 패리티 + 크로스모델 리뷰 |
| **Orchestration** | 역할 분업 + 루프 제어 | ★★★ 15에이전트·8워크플로우·루프가드 | ★★ 9역할 고정 + 예산·stop-after |

> **핵심 그림**: harness-test는 **Verification·Permission(가드레일)** 에서 앞서고,
> AutoAgent는 **Permission의 "승인 루프"와 크로스모델 검증**에서 앞선다. 서로의 빈틈을 메운다.

### 4.2 덱 패턴 채택

| 프레임워크 패턴 | harness-test | AutoAgent |
|-----------------|--------------|-----------|
| Plan → Execute | ✅ design→feature | ✅ preamble |
| Generate ↔ Review (GAN) | ✅ executor↔evaluator | ✅ **구현자↔반대모델(크로스모델)** |
| Router | ⚠️ 커맨드 수동선택 | ✅ route_task |
| Expert Team | ✅ 15 에이전트 | ⚠️ 9 역할(고정) |
| Parallel | ✅ parallel() | ⚠️ 제한적(decompose worktree, 미검증) |
| Human Approval | ❌ 거의 없음 | ✅ **승인 게이트+resume** |
| Tool Gate | ✅ policy 경로가드 | ⚠️ 권한모드/샌드박스 |
| Verification Loop | ✅ 3중 테스트 | ⚠️ dry-run+리뷰(실테스트 없음) |
| Memory/Evolution Loop | ✅ worklog·active-work | ⚠️ run 아카이브 |
| Worktree 격리 | ⚠️ 브랜치 단위 | ⚠️ decompose 레인별(routed/simple 비침투) |

### 4.3 근본 성향 차이

| | harness-test | AutoAgent |
|---|--------------|-----------|
| 하네스 위치 | 앱 레포 **안**(.claude 동거) | **외부** 오케스트레이터(타깃 분리) |
| 타깃 변경 | 직접 커밋·PR 생성 | **자동 커밋/푸시 안 함**(diff는 사람) |
| 모델 전략 | 역할별 **정적** 배치 | **크로스모델**(리뷰어=반대) + high-risk opus 승격 |
| 통제 방식 | **가드레일 강제**(정책·훅·테스트) | **승인 게이트** + 결정적 파이프라인 |
| 검증 신뢰원 | **결정론 테스트**(exit code) | 크로스모델 상호 리뷰 + dry-run 패리티 |
| 두께(덱 기준) | **두꺼움** | 중간 |

**공통점**(둘 다 프레임워크를 잘 따른 지점): 결정적 스크립트로 에이전트를 감쌈, 파일 기반
통신, 역할 분리, 루프 상한, 상태 외부화.

### 4.4 토론 포인트

1. **검증 vs 승인** — harness-test의 3중 결정론 게이트 vs AutoAgent의 사람 승인 게이트, 무엇이 먼저? 둘을 합치면?
2. **크로스모델의 값어치** — 두 모델 교차 비용 대비, 결정론 테스트로 품질 잡는 편이 싸지 않나? (덱: 자기평가 편향 → 외부 검증 필요)
3. **하네스 두께** — 우리 도메인은 harness-test급 두꺼움인가, AutoAgent의 중간인가?
4. **침투 vs 분리** — 앱 안(harness-test) vs 외부 오케스트레이터(AutoAgent), 재사용성 vs 밀착 자동화.
5. **비계 걷어내기** — 덱의 건강성 체크(강한 모델로 복잡도 없이 좋아지나? 일부 제거해도 품질 유지?)를 적용하면 어디가 과설계인가?
