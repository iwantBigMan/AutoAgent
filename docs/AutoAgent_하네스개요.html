AutoAgent · 하네스 개요
정의 철학 실행모델 파이프라인 역할 위험도 안전·검증 비교
Cross-model orchestration harness

두 모델이 교대로 구현하고
서로를 리뷰하게 만드는 로컬 하네스

AutoAgent는 Claude Code CLI와 Codex CLI를 서브프로세스로 구동해, 별도의 타깃 워크스페이스를 두 모델이 교대로 구현·리뷰하도록 조율한다. 핵심은 자율 루프가 아니라 비결정적 에이전트를 결정적 Python 제어 흐름으로 감싸는 것 — 무엇을 할지는 프롬프트가, 언제·누가·어떤 권한으로 실행할지는 코드가 정하고, 위험한 변경은 사람이 승인 게이트를 통과시켜야 코드가 바뀐다.

Claude (기획·구현·리뷰·보고) Codex (검증·리뷰·평가·구현) 사람 (승인 게이트)

01설계 철학 — 우리가 건 5개의 베팅

각 항목이 곧 토론 포인트다. "당신 하네스는 이 축에서 어디에 서 있나?"

01 크로스-모델 리뷰

CROSS-MODEL

리뷰어는 항상 구현자의 반대 모델. 같은 모델의 자기검토는 같은 맹점을 공유하므로, 모델을 교차시켜 적대적 다양성을 만든다.

02 코드가 조율, 프롬프트가 "무엇"

NEUTRAL CHANNEL

에이전트 행동은 prompts/**/*.md에, 오케스트레이션만 Python에. Codex는 Claude 스킬을 못 읽으므로, 두 CLI가 stdin으로 공유하는 중립 채널에 행동을 둔다.

03 사람 승인 게이트

HUMAN-IN-THE-LOOP

high-risk/db 구현은 코드 변경 전에 정지하고 --resume으로만 진행. "재개 실행 = 승인 행위". 게이트를 우회하는 블랭킷 플래그는 의도적으로 없다.

04 외부·비침투

NON-INVASIVE

타깃 레포는 안 건드리고, 상태는 하네스 레포에만, 자동 커밋/푸시 없음. 타깃은 오직 서브프로세스의 cwd로만 바라본다.

05 결정적 제어 흐름

DETERMINISTIC

루프·분기·예산·게이트가 전부 Python. 재현·감사 가능한 파이프라인이고, 에이전트가 "얼마나 도느냐"를 사람이 --max-agent-calls로 통제한다.

➜ 비교의 축

단일 모델 vs 크로스-모델 · 자율 루프 vs 고정 파이프라인 · 침투 vs 분리 · 규칙 vs 모델 판단. §08에 비교 매트릭스가 있다.

02실행 모델 — 가장 중요한 정신 모델

서브프로세스는 타깃 프로젝트를 cwd로 실행된다. 이 하네스 레포는 편집 대상이 아니라 조율자다.

# run.py --workspace C:\...\TargetProject --request "..."
run.py
  └─ 서브프로세스로 claude.cmd / codex.cmd 호출
       ├─ cwd    = config.workspace   ← 타깃 프로젝트 (이 하네스 레포 아님!)
       ├─ stdin  = render_template(prompt.md, values)  ← "무엇을 할지"
       └─ stdout = runs/<stamp>/NN_*.md 로 캡처         ← 산출물

입력

{VAR} 자리표시자를 가진 마크다운 프롬프트를 render_template이 값으로 치환해 stdin으로 주입.

격리

타깃은 cwd로만 접근. 하네스는 자동 커밋/푸시하지 않고, 산출물은 하네스 레포에만 남긴다.

산출물

runs/YYYYMMDD_HHMMSS/ (프로젝트 지정 시 projects/<name>/runs/<stamp>/)에 단계별 전부 기록.

모듈 지도

run.py                  진입점 → autoagent.cli.main
autoagent/

decompose 워크플로우 자체는 대규모 요청을 task_graph.json으로 분해만 하고 구현 단계를 절대 실행하지 않는다 — Claude는 --permission-mode plan, Codex는 --sandbox read-only로만 돌고, 그래프는 인간 승인에서 정지한다. 승인된 task_graph는 사람이 approval_brief.md를 검토한 뒤 --resume <run_dir>(checkpoint mode:"task_graph")로 재개하면 decompose 병렬 실행기(task_exec.py)가 실행을 맡는다(재개 = 승인 행위, 게이트 우회 아님).
decompose 병렬 실행기: git 베이스라인 확인 → task_graph 위상정렬(순환이면 halt) → 파도(wave)별 ThreadPoolExecutor(max_workers=max_parallel_lanes) 병렬 실행. 코드 노드(backend/frontend)마다 격리 git worktree + 레인 브랜치에서 구현→ 반대모델 리뷰→수정 미니 루프를 돌고, 완료 레인들을 통합 브랜치 aa-integration/<stamp>로 위상 순 순차 병합한다(충돌 시 stop-and-report). main은 미접촉, 자동 push 없음. 동시성 상한은 config.max_parallel_lanes (기본 2, 1이면 순차). dry-run·단위·코드리뷰까지 확인됐고, 라이브 end-to-end 실행은 아직 미검증이다.

05라우팅 & 위험도 — 설계 논쟁 지점

"위험도 체크는 db만 하나?" → 아니다. 두 층으로 판정하고, 각 층이 여러 신호를 본다.

라우팅 (route_task)

--task-type 명시 시 키워드 분류를 우회(탈출구). auto면 backend/frontend/docs 명사 키워드 점수 → 최고점, 0점이면 docs 기본. 구현 의도 가드: 명사가 docs를 가리켜도 구현 동사(구현/수정/추가…, implement/fix…)가 있으면 backend/frontend로 되돌린다.

안전 비대칭: 구현→docs 오분류(= 출력 없음)가 docs→backend 오분류(= 경로만 무겁고 출력은 맞음)보다 나쁘다 → 애매하면 구현 라우트로 편향.

위험도 — 두 층

# 1층 · 라우팅의 risk_level
db_score > 0 (DB_TERMS 20개)                          → subtype=db, high
high_risk_score > 0 (migration/auth/payment/production/backfill/rollback) → high
backend/frontend 일반                                 → medium   (frontend는 내용 무관 항상 medium)
docs/review                                           → low

# 2층 · 승인 게이트
approval_required = task_type∈{backend,frontend} and (--require-human-approval or is_high_risk)
is_high_risk      = risk_level=="high" or subtype=="db" or any(HIGH_RISK_REQUEST_TERMS)

⚠ 중복

1층 HIGH_RISK_TERMS ≡ 2층 HIGH_RISK_REQUEST_TERMS(동일 6단어). subtype=="db"도 db면 이미 high라 사실상 중복 → 한 곳만 고치면 어긋날 표면.

⚠ 공백

frontend는 절대 자동 high가 안 됨(플래그 없으면 게이트 미발동). 판정이 전부 키워드 substring이라 리스트 밖 위험(drop/truncate)은 놓칠 수 있음.

⚠ substring 취약

요청문이 하네스 코드를 설명하면 오작동. docs/specs 경로 → docs 오분류, db_score 심볼 → db 게이트 오발. 둘 다 교정 완료.

06안전 & 검증

안전 장치

• --read-only: Codex read-only 강제 + 구현 스킵
• 유효 Git HEAD 베이스라인 없으면 구현 차단
• decompose는 구현 절대 안 함, simple은 레거시 보존
• 자동 커밋/푸시/업로드 없음 — diff는 사람이 검토
• --max-agent-calls 예산 소진 시 정지(exit 0)
• --stop-after <stage> 단계별 정지

검증 (테스트 스위트 없음)

• --dry-run: CLI 호출 없이 프롬프트 + *_command.json 렌더링. 리팩터 전/후 바이트 동일성(SHA-256)으로 회귀 감지. dry-run은 예산 미포함.
• 도그푸딩: 이 하네스로 이 하네스를 구현·리뷰했고, 크로스-모델 리뷰가 실제 안전 회귀(DB 게이트)와 설계 갭(resume 경로)을 잡아냈다.

프로젝트별 워크스페이스 레지스트리

하네스가 여러 타깃에 재사용되므로 --project <name>으로 프로젝트 단위 분리.

# 설정 우선순위 (얕은 병합)
per-project config  >  global config  >  AUTOAGENT_WORKSPACE(env)  >  하드코딩 default

projects/<name>/config.json   # workspace + 선택 override
projects/<name>/runs/<stamp>/ # 그 프로젝트 실행 이력만

--project 미지정 시 동작·산출물 경로는 오늘과 100% 동일(하위호환).

열어둔 논쟁거리

  1. 키워드 라우팅은 싸지만 취약하다 — 모델 기반 라우팅으로 갈 가치가 있나?
