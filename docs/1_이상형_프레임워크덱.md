## 0. 한 줄 요약

> **AGENT = MODEL + HARNESS.** "모델은 요리사, 하네스는 주방." "원시 LLM은 운영체제
> 없는 CPU와 같다." — 좋은 답변은 모델만이 아니라 **모델이 일하는 환경**에서 나온다.
> 최종 명제: **"모델이 똑똑해질수록, 일하는 환경을 설계하는 힘이 더 중요해진다."**

## 2. 계층 사다리 — 단순 추론기에서 자율 시스템으로

```
레이어 1  Raw LLM      입력→출력, 단일 추론, 메모리·도구 없음
레이어 2  Subagent     LLM core + Tool(s) + Context, 반복 루프
레이어 3  Agent Team   협력 에이전트 + Orchestrator(계획·위임·집계)
레이어 4  Harness      전체 제어층 = Eval/Test + Retry/Guard + Routing + 흐름제어
```
> "계층이 올라갈수록 '모델이 혼자 할 수 없는 일'을 감싸는 인프라가 추가된다."

## 3. 왜 단순 에이전트는 실패하는가 (하네스의 존재 이유)

- **Context Degradation** — 컨텍스트가 커지면 임계점 이후 **크기와 추론 성능이 반비례**.
  compact은 정보를 유실시킨다.
- **Self-Evaluation Bias** — 자기 결과물을 과대평가 → 환각. 스스로의 판단만으론 품질
  보장 불가 → **외부 Evaluator + 상태 외부화**가 필요.

**컨텍스트 열화 수치** (슬라이드 원문 — "1M 윈도우라도 체감 품질 구간은 다르다"):

| 항목 | Sonnet 4.6 | Opus 4.6 / 4.8 |
|------|-----------|----------------|
| 컨텍스트 윈도우 | 1M | 1M |
| 벤치마크 정확도(1M) | **18.5%** | **76%** |
| 실사용 체감 고품질 구간 | ~100K | ~400K |

> 윈도우 크기 ≠ 실사용 품질. 모델별 저하 곡선을 알고 **세션을 끊어 줘야** 한다.

**Solo Agent vs Full Harness** (레트로 게임 구축 케이스):

| | 시간 | 비용 | 결과 |
|---|------|------|------|
| Solo Agent | 20분 | $9 | 핵심 게임플레이 미동작 |
| Full Harness | 6시간 | $200 | 물리엔진 + AI 통합 동작 |

> **난이도가 높을수록 하네스의 가치가 커진다.**

**설계를 좌우하는 4원칙**: ①하네스는 모델 능력과 함께 진화한다("모델이 못하는 것" 가정을
재검토) ②각 책임을 별도 에이전트에 위임 ③대화보다 파일 기반 통신 ④난이도 높을수록
Evaluator가 가치 있다. (Tip: 세션이 길어질수록 컨텍스트 노이즈 증가 → 세션 재시작)

## 4. 하네스의 구성

### 4.1 여섯 종류
Context(가이드·정보 제약) / Permission(할 수 있는·없는 일, 되돌릴 수 없는 실행 분리) /
Verification(자동검증=테스트·타입, 구조검증=변경·아키텍처) / Tool(CRUD·skill·mcp·api
제약, 전후 hook) / Subagent & Worktree(병렬 시 코드·컨텍스트 격리) / Debugging(규약대로 수정).

### 4.2 제품급 12요소

| # | 구성요소 | 비유 | 역할 |
|---|----------|------|------|
| 1 | 목표·성공기준 | 주문서 | 무엇을 끝으로 볼지 |
| 2 | 오케스트레이션 | 흐름표 | 호출·실행·반영 반복 |
| 3 | 도구 레이어 | 손과 발 | 검색·파일·API |
| 4 | 메모리 | 업무 노트 | 세션 안팎 정보 보관 |
| 5 | 컨텍스트 관리 | 책상 정리 | 지금 볼 자료만 선별 |
| 6 | 프롬프트 구성 | 안건지 | 지시·도구·메모리 조립 |
| 7 | 출력 파싱 | 접수 담당 | 답변/도구호출 구분 |
| 8 | 상태·체크포인트 | 저장 버튼 | 재개·되돌리기·디버깅 |
| 9 | 오류 처리 | 고객센터 | 재시도·복구·개입 |
| 10 | 가드레일·권한 | 출입카드 | 위험 차단·승인 |
| 11 | 검증 루프 | 검사관 | 테스트·리뷰·평가 |
| 12 | 관측성·분업 | CCTV | 로그·비용·subagent |

### 4.3 메모리·스킬·프로토콜·중재장치
- **메모리 4유형**: Working Context / Semantic Knowledge / Episodic Experience / Personalized Memory.
- **스킬 = 반복용 컨텍스트**: 운영 절차 / 판단 기준 / 반드시 지킬 규칙.
- **프로토콜 = 상호작용 계약**: Agent-to-User / Agent-to-Agent / Agent-to-Tools.
- **중재장치 6종**: Sandboxing / Observability / Compression / Evaluation / Approval Loops / Sub-Agent Orchestration.
- **비유**: 회사 운영 = 직원(모델) + 업무노트(메모리) + 매뉴얼(스킬) + 보고체계(프로토콜) + 결재·감사(중재장치).

### 4.4 하네스 루프 7단계
프롬프트 조립 → LLM 추론 → 출력 분류 → 도구 실행 → 결과 패키징 → 컨텍스트 업데이트 →
반복/종료. **종료 조건 5종**: 최종답변 · 턴 제한 · 토큰 예산 · 가드레일 · 사람 승인.
> "오류는 숨기지 말고 관찰 메시지로 돌려보낸다." / "루프 품질은 모델 호출보다 각 단계 사이의 연결·검증에서 결정된다."

### 4.5 역할 5종 · 분업 3형태
- **역할**: Planner(목표 분해) / Researcher(자료 찾고 요약) / Builder(결과물 생성) /
  Evaluator(비판적 검증) / Reporter(사람용 보고서). "에이전트를 많이 만들면 좋다? → 아니다. 목적이 있을 때 분업."
- **분업**:

  | 형태 | 언제 | 주의 |
  |------|------|------|
  | **Fork** | 독립 조사·코드 리뷰·대안 생성 | 결과 요약 잘해야 부모 오염 방지 |
  | **Teammate** | 긴·병렬 작업, 지속 QA | 누가 무엇을 했는지 기록 |
  | **Worktree** | 코드 수정·실험·위험한 변경 | merge·충돌 정책 필요 |

## 5. 패턴 카탈로그

| 패턴 | 무엇을 | 어떻게 | 언제 |
|------|--------|--------|------|
| **GAN loop (2-agent)** | Generator ↔ Evaluator 적대 반복 | Generator(HTML/CSS/JS, Claude Agent SDK) ↔ Evaluator(Playwright MCP 렌더·채점), 5~15회/~4h | 자동 시각 검증 가능한 UI |
| **3-agent loop** | Planner→Generator→Evaluator | 1~4문장→제품 스펙 → React/Vite/FastAPI/SQLite 한 기능씩 Git 커밋 → Playwright로 UI→API→DB 검증 | 난이도 높은 풀스택 |
| **Ralph loop** | 컨텍스트 매 루프 초기화 + 상태 외부화 | feature_list.json·progress.md·git·test report + Handoff(목표/완료/진행중/다음행동/주의점), init.sh+smoke test | 검증 가능한 긴 작업(테스트·리팩터·DB). 토큰 비용 큼, 주관·실시간 부적합 |
| **Permission harness** | 허용/승인/금지 3분할 | 읽기·초안·검색=허용, 메일·결제·삭제=승인, 비밀번호·권한변경·개인정보=금지. settings.json 통제 + 전 행동 로깅 | 되돌릴 수 없는 작업 포함 시 |
| **Tool design P1~P6** | 도구를 에이전트 친화적으로 | P1 고임팩트 통합(1:1 X)·P2 접두사 네임스페이싱·P3 의미식별자·response_format·P4 페이지네이션 기본·P5 설명 엔지니어링·P6 실행가능 오류. 출력=상위5개 요약·불확실성 표기 | 항상 |

**Ralph loop 실패 방지**: "너무 일찍 완료"→feature list 먼저 읽게 / "버그 둔 채 인계"→실패
테스트·로그를 progress에 / "실제 흐름 미확인"→브라우저 검증·스크린샷 / "매번 실행법 재탐색"→
init.sh+smoke test. (Git commit = "작업 일지")

## 6. 얇은 vs 두꺼운 하네스

프레임워크 두께 스펙트럼:
`Claude Agent SDK(얇음) → OpenAI Agents SDK → CrewAI Flow → LangGraph(두꺼움)`

- **얇은 하네스** — 모델 자율성 신뢰. 단순·유연, 새 모델 이점 빨리 흡수. 탐색·창작·코드보조.
- **두꺼운 하네스** — 흐름을 코드로 명시. 예측·감사 가능, 복잡 업무 통제. 규제·결제/배포·
  고위험·다단계. 상태그래프·명시 라우팅·검증 노드.

> **하네스 두께는 취향이 아니라 위험도·반복성·실패 비용에 대한 설계 결정이다.**
> "하네스는 비계처럼 세우고, 쓰고, **걷어내고**, 다시 조정한다." (학습된 하네스를 갑자기 비우면 성능 급락)

**설계 전 7가지 질문**: 단일 vs 멀티 / ReAct vs 계획후실행 / 강한압축 vs 풍부한컨텍스트 /
계산적 vs 추론적 검증 / 허용적 vs 제한적 / 전체 vs 최소 도구 / 얇은 vs 두꺼운.

**건강성 체크**: ①더 강한 모델로 바꾸면 복잡도 없이 성능↑? ②일부 제거해도 품질 유지?
③실패 시 trace/log/eval로 원인이 보임? ④비계 제거 후 회귀 평가가 있음?

## 7. 보안 — 프롬프트 인젝션

- **유형**: Direct(입력창에 악성 명령) / Indirect(문서·웹에 숨은 명령) / Jailbreak(역할극·페르소나로 우회).
- **3계층 방어**: ①입력 검증(패턴 필터·길이 제한·인코딩 정규화 유니코드·base64) ②권한 분리
  (샌드박스·최소 권한·데이터/명령 분리) ③출력 검증(민감정보 필터·인간 검토·이상행동 탐지).
- 원칙: **"외부 데이터는 항상 '데이터'로만 취급, 절대 '명령'으로 실행 금지."**

## 8. 실전 — 12패턴 · 성장 로드맵 · 7계층 · 설계선택

- **12 실전 패턴**: 단일 에이전트 / 계획-실행 / 생성-검토 / 라우터 / 전문가 팀 / 감독자 /
  병렬 / 순차 파이프라인 / 사람 승인 / 메모리 루프 / 도구 게이트 / 진화 루프. 선택 기준 = 위험도·반복성·복잡도.
- **성장 로드맵 5단계**: 프롬프트 → 컨텍스트 → 도구 → 검증 → 운영 하네스 (지지축: 권한·로그·개선).
- **모델 위 7계층 피라미드**: ①모델 ②도구·API ③컨텍스트·메모리(=능력) ④오케스트레이션
  ⑤평가·추적 ⑥보안·거버넌스 ⑦제품 경험(=운영). 사용자 가치 = 최상.
- **에이전트 친화적 설계**: 명확한 파일명·폴더 / 짧은 AGENTS.md + 구조화 docs / 빠른 테스트·린터 /
  읽기 쉬운 로그·trace / 작은 PR·작은 작업 단위 / 기계가 읽는 설정·스키마.
- **실전 5패턴**: 점진적 공개 / 작업공간 격리(샌드박스·브랜치·worktree) / 저장소=지식공간
  (정책·스펙·완료기준·아키텍처 원칙) / 기계적 아키텍처 강제 / 통합 피드백 루프(로그·trace).
